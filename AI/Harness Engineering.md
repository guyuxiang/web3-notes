# Harness Engineering

**Harness Engineering（编排工程 / 控制工程）**指的是：

👉 **围绕大模型（如 OpenAI 的 GPT 系列）构建一整套“控制系统”，让 AI 能可靠执行复杂任务**

你可以把它理解为：

> ❌ 不是单次 Prompt
>  ✅ 而是一个“AI 工作流系统 + 约束 + 验证 + 多轮交互”的组合，用工程手段“管住 AI”



**人负责：目标、约束、反馈**
 **AI（Codex）负责：执行所有具体工作**



### Harness = 一整套控制系统

包括：

- 指令（prompt / spec）
- 工具（CLI、API、测试工具）
- 约束（规则、格式、接口）
- 反馈（测试结果、报错、日志）



## 反馈回路（Loop）

这篇文章最关键的工程思想：

> **AI 必须在循环中工作，而不是一次性输出**

典型流程：

```
生成代码 → 运行 → 报错 → 修复 → 再运行
```

文章强调：

> **可靠性来自“循环 + 反馈”，而不是模型本身**



## 工程师的角色：

- 设计任务（spec）
- 设计环境（tools / repo）
- 设计反馈（tests / logs）

从“程序员” → “系统设计师 / AI 管理者”



## 具体做法

## 1️⃣ 明确“意图”（Spec First）

AI 不懂“模糊需求”，所以必须：

- 写清楚目标
- 写清楚约束
- 写清楚接口

👉 类似：

- PRD（产品需求文档）
- API contract

------

## 2️⃣ 构建工具环境（Tooling）

给 AI 配“工具箱”：

- CLI 工具
- 浏览器控制（DevTools）
- 测试工具
- 日志系统

👉 AI ≠ ChatGPT
 👉 AI = “可以操作世界的程序”

------

## 3️⃣ 强制验证（Tests / CI）

文章反复强调：

> ❗ **测试是控制 AI 的核心手段**

比如：

- 单元测试
- 集成测试
- 自动 CI

AI 写完代码后：

👉 不问“对不对”
 👉 直接跑测试

------

## 4️⃣ 持续修复环境（不是修代码）

一个很反直觉的点：

> ❌ AI 写错 → 手动改代码
>  ✅ AI 写错 → 改“系统/规则”

例如：

- 修改 prompt
- 修改 AGENTS.md
- 加新工具
- 加约束

👉 目标是：

> **让错误“不会再发生”**



## 哲学

#### 1️⃣ 软件工程正在“控制论化”

不是写代码，而是：

> **设计一个能自我修正的系统**

------

#### 2️⃣ Prompt Engineering 已经不够

文章隐含批评：

- prompt 只是输入
- 但真正关键是：
  - 工具
  - 结构
  - 反馈系统

------

#### 3️⃣ 人类的稀缺资源变了

文章原话强调：

> 要最大化“人类的时间和注意力” 

所以：

- 人类做决策
- AI 做执行
